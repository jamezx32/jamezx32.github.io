# 调用约定与寄存器

## 概述

这份笔记的起点是一次很憋屈的段错误：ROP 链逻辑全部正确——gadget 存在、地址算对、参数就位——第一次跑就 SIGSEGV，崩点在 libc 内部一条与我无关的 `movaps` 上。排查到最后发现根源只有一句话：**栈没按 ABI 对齐**。链里的每一步单看都能跑，合起来却违反了所有参与方默认遵守的合同。

调用约定（calling convention）就是这份合同：参数放哪些寄存器、返回值放哪、哪些寄存器跨调用必须保真、栈在调用瞬间必须是什么形状。编译器、libc、引擎的 JIT 代码都按它生成指令——exploit 要把执行流劫持进这些代码，就得按同一份合同布置现场。

下面按我当时补课的顺序整理：先认识 x86-64 的通用寄存器，再过 SysV AMD64（Linux/macOS）和 Windows x64 两套约定，然后是 syscall 与 ARM64，最后回到那条崩掉的链，把教训收成一张 checklist。

## 从一次段错误说起

先看事故现场，后面所有规则都能在这件事里找到位置。

链的目标很普通：跳进 libc 的 `jmp rax` 型 gadget，把执行流转给 `system`。在把它塞进真实 exploit 之前，我照例先搭了个独立测试床（不经引擎，C 当调用方）：

```bash
# harness.py:读 /proc/self/maps 拿本进程 libc 基址 →
#            mmap 一页 RWX 放 shellcode → 读 gadget 前两个字节验证 → 当函数调用
python3 harness.py
# [*] gadget @ 0x…eba verified: ffe0 (jmp rax)
# Segmentation fault              ← 第一次跑就崩
```

gdb 看崩点：

```bash
gdb -q -batch -ex run -ex 'x/4i $rip' --args python3 harness.py
# => movaps XMMWORD PTR [rsp+0x…],xmm0    ← 崩在 libc 内部的对齐访问
```

`movaps` 要求操作数 16 字节对齐。glibc 内部函数假设"进入我时 rsp ≡ 8 (mod 16)"（下面推导），据此用了对齐指令；而我的链经 `jmp` 进 gadget、gadget 又 `jmp` 进 system，全程没有 `call`——`call` 会 push 8 字节返回地址，恰好把对齐补上——于是 system 入口的 rsp 差了 8。修复是给 shellcode 加一对垫片：

```text
sub rsp, 8     ; 进入时先挪 8 字节，让最终 system 入口回到 ≡ 8 (mod 16)
...（压栈布置链）...
add rsp, 8     ; 返回时再挪回去
```

加完垫片，同一条链一次通过。这次崩溃教会我的是：**ABI 不是文档里的建议，是指令级别的假设**——破坏它的人不报错，深处的人替你崩。

## x86-64 通用寄存器

16 个通用寄存器，每个都有 64/32/16/8 位别名（`rax`/`eax`/`ax`/`al`），写 32 位别名会自动清零高 32 位。按"性格"分组记比按编号记快：

| 寄存器 | 典型角色 |
|---|---|
| **RAX** | 乘除指令的固定搭档（与 RDX 成对）；函数**返回值**；Linux **syscall 号**。 |
| **RBX** | callee-saved，常当临时基址或长期活跃值。 |
| **RCX** | 移位计数在低 8 位 **CL**；SysV 第 4 参；Windows **第 1 参**；`rep` 串指令的计数器。 |
| **RDX** | 与 RAX 搭档做乘除（高半/余数）；SysV 第 3 参、Windows 第 2 参；syscall 第 3 参。 |
| **RSI** | **源指针**（串指令）；SysV 第 2 参；syscall 第 2 参。 |
| **RDI** | **目标指针**（串指令）；SysV **第 1 参**；syscall 第 1 参。 |
| **RBP** | 传统**帧指针**（可省略）；callee-saved。 |
| **RSP** | **栈指针**，栈向低地址生长；`push` 先减后存、`pop` 先取后加。 |
| **R8–R11** | 纯临时、caller-saved；SysV 第 5–6 参在 R8/R9；Windows 第 3–4 参在 R8/R9。 |
| **R12–R15** | callee-saved，适合长期活跃值、基址。 |

三个角色值得单独点名：RDI 是 SysV 的"第一参数位"，直接决定了 `pop rdi ; ret` 是 x86-64 上最万能的 ROP gadget；RSP 的纪律（对齐、进出平衡）就是上面那次崩溃的主角；callee-saved 那组（RBX/RBP/R12–R15）决定了"从 ROP 链干净返回宿主"是否可能。

## SysV AMD64

Linux、macOS、BSD 等 Unix 系 x86-64 系统共用 System V AMD64 ABI。规则不长：

**参数传递**：前六个整数/指针参数依次放 `RDI, RSI, RDX, RCX, R8, R9`，其余走栈（从第 7 个开始）。浮点参数走 XMM0–XMM7，与整型序列各自独立编号。

**返回值**：放 RAX；128 位返回值用 RDX:RAX 一对。

**寄存器保存**：

- caller-saved（调用后不可假设仍成立）：RAX, RCX, RDX, RSI, RDI, R8–R11, XMM0–XMM15——调用方想留着就得自己存；
- callee-saved（被调方必须原样归还）：RBX, RBP, R12–R15。

**栈对齐**：`call` 指令执行前 RSP 必须 16 字节对齐。`call` 会把 8 字节返回地址压栈，所以推论是：**函数入口处 RSP ≡ 8 (mod 16)**。编译器按这个假设生成 prologue 和对齐访问（`movaps` 一类 SIMD），假设不成立就在函数深处崩——回到那次段错误，`jmp` 型 gadget 的问题正是绕过了 `call`，少压了那 8 字节。

```text
调用方：RSP ≡ 0 (mod 16)
    │ call system        ← push 返回地址(8B)
    ▼
system 入口：RSP ≡ 8 (mod 16)，[RSP] = 返回地址
```

手工调函数（C 测试床也好、ROP 也好）对照这张速查就够了：第一个参数进 RDI、返回地址压在栈顶、入口对齐 ≡8、别碰 RBX/RBP/R12–R15 不还。

## Windows x64

同一颗 CPU，另一份合同。差异集中在三点：

**参数传递**：前四个整数/指针参数放 `RCX, RDX, R8, R9`，第 5 个起走栈——比 SysV 少两个寄存器位。

**Shadow Space**：调用方必须在栈上为被调方预留 32 字节（4 × 8B），即使参数全走寄存器。这 32 字节位于返回地址下方，被调方可以用来溢写寄存器参数（调试器抓寄存器现场也靠它）。手工调 Windows 函数时少预留这 32 字节，是和栈不对齐同级别的经典崩溃源；写 Windows ROP 链时，每个调用目标前都要安排这 32 字节的空槽。

**寄存器保存**：callee-saved 名单比 SysV 长——RBX, RBP, **RSI, RDI**, R12–R15, **XMM6–XMM15**。RSI/RDI 在 SysV 里是易失的参数寄存器，在 Windows 里却要被调方保真——同一份 shellcode 跨平台时容易在这里踩差异。

## 两种约定对比

| 规则 | SysV AMD64（Linux/macOS/BSD） | Windows x64 |
|---|---|---|
| 第 1–4 个参数 | RDI, RSI, RDX, RCX | RCX, RDX, R8, R9 |
| 第 5–6 个参数 | R8, R9 | 栈 |
| 返回值 | RAX | RAX |
| caller-saved | RAX, RCX, RDX, RSI, RDI, R8–R11, XMM0–XMM15 | RAX, RCX, RDX, R8–R11, XMM0–XMM5 |
| callee-saved | RBX, RBP, R12–R15 | RBX, RBP, RSI, RDI, R12–R15, XMM6–XMM15 |
| 栈对齐 | call 前 16 字节对齐 | call 前 16 字节对齐 + 32 字节 shadow space |

两个版本间迁移的改动点顺带记下：偏移型 shellcode 里所有 `pop rdi/rsi` 换成 `pop rcx/rdx`；每个调用点补 32 字节空槽；RSI/RDI 从"随便用"升级为"用完要还"。

## syscall 约定

shellcode 不经 libc 直接陷内核时，用的是另一套寄存器约定（Linux x86-64）：

| 角色 | 寄存器 |
|---|---|
| syscall 号 | RAX |
| 参数 1–6 | RDI, RSI, RDX, **R10**, R8, R9 |
| 返回值 | RAX（负数即 -errno） |
| 附带损毁 | RCX（存返回地址）、R11（存 rflags） |

注意第 4 参是 **R10 不是 RCX**——`syscall` 指令硬件上会动 RCX/R11，所以内核 ABI 把第 4 参挪去了 R10，这是与 C 约定最容易记混的一处。最常写的 `execve` 是整套约定的最小示例：

```text
RAX = 59        ; execve
RDI = "/bin/sh" ; path
RSI = argv      ; char**（可为 0）
RDX = envp      ; char**（可为 0）
syscall
```

macOS 同属 SysV，C 层函数调用与 Linux 完全一致；差异在 syscall 层：号不同且按类分段，Unix 类 syscall 号要加 `0x2000000` 前缀（如 `write` 是 0x2000004）。跨平台 shellcode 别直接照抄 Linux 的号表。

## ARM64：Apple Silicon 与 iOS

Safari/JSC 的在野利用大多落在 iOS / Apple Silicon 上，那边是 ARM64（AArch64，约定名 AAPCS64），对应关系顺手记全：

- **参数**：x0–x7 传前 8 个参数，浮点走 v0–v7，其余走栈；**返回值在 x0**；
- **专用寄存器**：x29 是帧指针（FP）、x30 是链接寄存器（LR）——`bl` 把返回地址放进 x30 而不是压栈，`ret` 跳的就是 x30。这意味着 ARM64 的返回地址默认**在寄存器里**，只有大型函数才把它 spill 到栈上——ROP 的 gadget 形态因此不同，典型是 `ldp x29, x30, [sp], #…; ret` 这种"从栈恢复 LR 再返回"的组合；
- **栈**：SP 强制 16 字节对齐（硬件要求），没有 shadow space；
- **callee-saved**：x19–x28、x29、x30（浮点 d8–d15 同理）；x18 是平台寄存器，iOS 上保留给系统，用户代码别碰；
- **syscall**：号在 **x8**、参数 x0–x5、指令 `svc 0x80`（macOS 同为 `svc 0x80`，号分类）。

从 x86-64 迁过去最大的心智转换就一条：x86 的控制流真相在**栈上**（返回地址、ROP 链都是栈内容），ARM64 的控制流真相在 **x30 与栈的混合**上——劫持执行流先问一句"返回地址此刻在哪"。

## 回到那条链：手工调函数的 checklist

把全文收拢成一张我每次布链前过的清单（对照那次 movaps 崩溃逐条打钩）：

```text
1. 参数就位：第一个参数在 RDI（Windows: RCX），第二个在 RSI（Windows: RDX）……
2. 返回地址在栈顶：gadget 的 ret / call 的落点由你布置，不是碰运气；
3. 栈对齐：进入目标函数那一刻 RSP ≡ 8 (mod 16)；
   —— jmp 型 gadget 不压返回地址，垫片方向与 call 型相反，两种别混用；
4. Windows 目标：call 前留 32 字节 shadow space；
5. callee-saved 保真：RBX/RBP/R12-R15（Windows 另有 RSI/RDI）动过就要恢复，
   否则链返回后宿主引擎随时崩在你留下的脏现场里；
6. 自校验：进目标前先在测试床里让 gdb 单步到入口，
   x/i $rip 看落点、p/x $rsp 验对齐。
```

第 6 条是那次崩溃之后加的：与其猜，不如让 gdb 替你确认一次入口现场——成本半分钟，省掉的是一轮"链明明没错却崩在 libc 深处"的排查。
