# V8 沙箱机制

## 概述

写多了 V8 的利用会碰上同一堵墙：addrof/fakeobj 做出来了、堆内任意读写也有了，然后呢？本站的几个案例正好展示了两种命运——[CVE-2021-30517](CVE-2021-30517分析.md) 那个年代，堆内读写直接升级成进程读写、覆盖 wasm RWX 页、执行 shellcode，一条龙走完；而在新版本上，同样的原语会在半路被拦住：你能破坏的只剩 V8 自己的堆，进程的其它内存碰不到。这堵墙就是 **V8 沙箱（V8 sandbox）**。

沙箱的思路一句话就能说清：**既然"引擎出 bug 导致堆内任意读写"无法根绝，那就假设它已经发生，把损害限制在一个固定的内存区域内**。它是一个纯软件的、进程内的隔离机制——不开子进程、不靠系统沙箱，靠的是把堆里所有"指向外部世界的裸指针"和"能放大成外部破坏的字段"改造掉。

时间线：从设计到落地花了三年左右；按 2024 年 4 月官方博客的说法，64 位平台的 Chrome 里它已默认开启了约两年，Chrome 123 起"转正"（沙箱逃逸纳入 VRP 赏金类目）。性能开销实测在典型负载上约 1% 以内——这也是它能默认开启的前提。

## 威胁模型

沙箱明确假设：**攻击者已经拿到沙箱内的任意读写**。注意这个假设有多激进——它不是在防"漏洞发生"，而是在防"漏洞发生的后果"：

```text
沙箱前的经典链(本站 30517 就是活标本):
  引擎 bug → addrof/fakeobj
    → 改写 JSArrayBuffer 的 backing_store 裸指针(想读哪写到哪)
    → 进程级任意读写
    → 定位 wasm RWX 页,写入 shellcode
    → 代码执行

沙箱后的同一条链:
  引擎 bug → addrof/fakeobj → 堆内任意读写
    → backing_store 不再是裸指针(是沙箱内偏移)
    → 破坏只能落在沙箱内 —— 链条到此为止
```

对利用者的含义：**沙箱内的破坏依然免费**（本站 [38003](CVE-2021-38003分析.md)、[12433](CVE-2025-12433分析.md) 那些在一块堆内存上做的手术全部照旧成立），但从"堆内读写"到"进程读写"之间多了一道必须再找一个 bug 才能穿过的大门——这个 bug 类别就是沙箱逃逸（sandbox escape，Chromium 里标 SBX）。

## 沙箱布局

沙箱在 64 位进程的地址空间里保留**约 1 TB**（外加两侧护栏区），所有与 V8 堆相关的内存都住进去：

```text
进程地址空间(示意)
┌────────────────────────────────────────────────────────┐
│ V8 沙箱(约 1TB 保留区)                                   │
│ ┌────────────┐ ┌────────────────────────────────────┐ │
│ │ 指针压缩笼 │ │ 沙箱内的其它内存:                    │ │
│ │ (4GB,V8 堆)│ │  ArrayBuffer 后备存储、WASM 线性内存 │ │
│ └────────────┘ └────────────────────────────────────┘ │
├────────────────────────────────────────────────────────┤
│ 沙箱外:线程栈、外部指针表/可信指针表/代码指针表、          │
│       可信空间(BytecodeArray/Code/WasmTrusted 实例数据)、│
│       可执行内存(JIT/wasm 代码)、embedder 对象、libc……   │
└────────────────────────────────────────────────────────┘
```

两个配套的"收口"设计：

- **沙箱内不再有 64 位指针和 64 位长度**。指向沙箱内其它位置的数据用 `sandbox_ptr_t`——相对沙箱基址的 **40 位偏移**（1TB 恰好 2^40）；长度用 `sandbox_size_t`，上限 32 GB。改写这类字段最多把视野指到沙箱内另一处，指不出去——`JSArrayBuffer` 的 `backing_store`/`byte_length` 就是这么改造的，30517 式"改 backing_store 拿任意读写"从根上失效。
- **栈必须留在沙箱外**（硬件/OS 要求栈上放裸指针，比如返回地址），所以栈不在此防线内——但脚本本来也没有直接写栈的通道。

沙箱建在[指针压缩](V8指针压缩机制.md)的地基上：4GB 压缩笼放在沙箱开头，压缩指针天然就是"沙箱内偏移"，两套机制共享同一个"基址 + 偏移"的世界观。

## 指针表三件套

堆里的对象不可避免要引用沙箱外的东西（C++ 侧的 embedder 对象、可执行代码、可信元数据）。沙箱的做法是**把裸指针全部换成表间接**——官方类比是 Unix 文件描述符表：堆里存的是"句柄"（表内索引），真指针躺在沙箱外的表里，攻击者的堆内写破坏只能改到句柄（换个索引），改不到真指针本身。三张表各管一类：

| 表 | 管什么 | 典型引用者 |
|---|---|---|
| **外部指针表（EPT）** | 指向沙箱外非 V8 对象的指针（embedder 数据、ArrayBuffer 的外部资源等） | 各类持有外部资源的 JS 对象 |
| **可信指针表（TPT）** | 指向"可信空间"里 V8 对象的引用 | 堆对象对 BytecodeArray、WasmTrustedInstanceData 等的引用 |
| **代码指针表（CPT）** | 可执行代码入口 | JSFunction 的 code 字段 |

两个关键细节：

- **表项带类型标签**。EPT 的表项里除了指针还有 tag，加载时校验"取出来的指针类型对不对"——这防住了"把 A 类型的句柄当 B 类型用"的廉价错位（不同资源混用一张表时靠 tag 分席）。历史上的逃逸研究里，"两个资源共用同一个 tag"就是一整类攻击面。
- **可信空间（trusted space）是堆外的 V8 对象区**。`BytecodeArray`、`Code`、wasm 的可信实例数据这些"一旦被篡改就直接升级为逃逸"的敏感对象整体搬出了沙箱，堆内对象经 TPT 间接引用。JSFunction 调用代码则经 CPT：堆内能改的只剩"选表里哪一项"，改不出任意的代码入口。

此外还有一道 **SBXCHECK**：对"攻击者可破坏、又被外部逻辑信任"的不变量（比如拿堆内计数值去索引沙箱外的 `std::vector`）加显式边界检查——命中即崩溃，宁可死也不越界。

## WASM 的变化

wasm 是旧利用链的常客（RWX 页、函数表里的裸指针），沙箱对它动得也最狠：

- **wasm 线性内存**作为普通后备存储放进沙箱——改它的长度/基地址字段，视野也出不了沙箱；
- **wasm 代码与可信实例数据**（编译产物、内部函数表等）搬进可信空间，经 TPT/CPT 间接引用；
- 30517 那条"写 wasm RWX 页"的出口被整个封死：JIT/wasm 的可执行内存都不在沙箱里，堆内读写根本够不着。

这条防线的实际效果也被真实攻击印证过反面：Theori 对 2024 年一条在野链沙箱逃逸段的分析（[链接](https://theori.io/blog/a-deep-dive-into-v8-sandbox-escape-technique-used-in-in-the-wild-exploit)，也是 [CVE-2024-5274 分析](CVE-2024-5274分析.md)参考条目之一）展示的逃逸手法正是"可信数据结构里残留的裸指针"（`WasmIndirectFunctionTable` 一类）——5274 的类型混淆负责打进渲染器，逃逸段还要再找一个这类洞才能到进程级。

## 攻击面的变化

对写利用的人，沙箱把工作切成了明确的两段：

**沙箱内（不变）**：找引擎 bug 拿堆内读写——[38003](CVE-2021-38003分析.md) 的 Map 双删、[12433](CVE-2025-12433分析.md) 的误折叠、[5274](CVE-2024-5274分析.md) 的换 Map，这些手术全部只动沙箱内的内存，沙箱时代照做。

**逃逸段（新战场）**：从"堆内读写"到"进程读写"要单独找 SBX 类 bug，常见方向：

1. **指针表的标签混淆**——两个资源共用 tag、或某条加载路径漏校验 tag，句柄错位后拿到别类的真指针；
2. **漏改造的裸指针/漏加的 SBXCHECK**——新 API、新数据结构落地时没跟上沙箱纪律（上面 WasmIndirectFunctionTable 的例子、以及 TPT 相关的公开研究都属于这类）；
3. **"沙箱内数据被外面信任"**——堆内字段（长度、计数、索引）流进沙箱外的 C++ 逻辑时没做检查，SBXCHECK 补的就是这类，但补全是个持续过程。

这也解释了为什么 SBX 在 VRP 里是单独的高赏金类目：它和"打进沙箱"是两道独立的墙，攻击链必须各破一次。

## 实验与调试

```bash
# 确认构建开了沙箱(gn 参数)
gn args out/x64.release --list | grep v8_enable_sandbox

# d8 的内存破坏实验 API:专门为"假设已有堆内读写"的逃逸研究准备
./d8 --sandbox-testing escape.js
#   Sandbox.getAddressOf(obj)   —— addrof
#   Sandbox.MemoryView(addr, n) —— 堆内读写视图
#   --sandbox-fuzzing           —— 同 API,fuzzing 导向
# 触发沙箱违例时,专用信号处理器会把 SIGSEGV 报成"sandbox violation",
# 与普通崩溃区分开

# 看沙箱的 1TB 保留区(真实进程里肉眼可见这堵墙)
gdb -q -batch -ex 'break main' -ex run -ex 'info proc mappings' --args ./d8 -e 1
#   在映射表里找一块 ~1TB 的保留区域,起点即沙箱基址
```

这套实验 API 的设计哲学值得记一笔：它**主动发放**堆内读写（沙箱威胁模型里假设攻击者已有的能力），让研究者把精力全部花在逃逸段上——相当于官方把"第一步"标准化了。

## 博客案例的坐标

把本站已有的 V8 案例放进沙箱坐标系里看：

| 案例 | 泄漏/原语 | 沙箱视角 |
|---|---|---|
| [CVE-2021-30517](CVE-2021-30517分析.md) | SuperIC 混淆 → 任意读写 → wasm RWX | 沙箱前的完整链；后半程（进程读写 + RWX）在沙箱时代已走不通 |
| [CVE-2021-38003](CVE-2021-38003分析.md) | TheHole → OrderedHashMap → addrof/fakeobj | 手术全部在堆内，沙箱时代照旧成立 |
| [CVE-2024-5274](CVE-2024-5274分析.md) | NativeContext 别名 → 换 Map → addrof/fakeobj | 同上；其配套的在野链逃逸段（Theori 分析）正是 SBX 的活标本 |
| [CVE-2024-2887](CVE-2024-2887分析.md) | Wasm GC 类型混淆 → addrof/fakeobj | 同上；ZDI 链里 GSAB 下溢扩展的也是沙箱内读写 |
| [CVE-2025-12433](CVE-2025-12433分析.md) / [CVE-2025-12429](CVE-2025-12429分析.md) | TDZ 家族 → 误折叠 → OOB → 任意读写 | 堆内全流程；到"进程读写"一步在沙箱时代需另寻 SBX |

一句话总结坐标系：**本站所有案例的前半程（到堆内任意读写）都是沙箱无关的；分水岭在"怎么把堆内读写变成进程读写"——沙箱把这一步从"改个指针"变成"再找一个 bug"**。
