# V8 调试手册

## 概述

本文记录 V8 漏洞分析常用的源码获取、构建配置、`d8` 参数、`gdb` 辅助命令和分析流程。命令以 Linux x64 为准，macOS 仅构建方式不同（需装 Xcode），`d8` 参数与 gdb 流程通用。

漏洞复现建议准备两个构建目录（按需选一或都建）：

| 构建目录 | 用途 |
|---|---|
| `x64.debug` | 源码调试、断点、DCHECK、对象打印 |
| `x64.release` | 漏洞复现（快）；如需 gdb 符号加 `symbol_level=1` |

## 源码获取

### 安装 depot_tools

```bash
git clone https://chromium.googlesource.com/chromium/tools/depot_tools.git ~/depot_tools
echo 'export PATH="$HOME/depot_tools:$PATH"' >> ~/.bashrc
source ~/.bashrc
gclient    # 首次运行自更新
```

`depot_tools` 应放在 `PATH` 最前面，避免系统自带的 `gn` / `ninja` 抢占。

### 获取源码

```bash
mkdir ~/v8 && cd ~/v8
fetch v8
cd v8
```

`fetch` 完成后仓库处于 detached HEAD 状态——这是正常的。

Linux 需额外安装系统依赖：

```bash
./build/install-build-deps.sh
```

### 切换到指定版本

漏洞分析的核心动作——切到修复 commit 的**父提交**（即漏洞最后存活的版本）：

```bash
cd ~/v8/v8
git fetch --tags
git checkout <commit>
gclient sync -D          # 把 DEPS 依赖同步到该版本并删旧目录
```

不跑 `gclient sync -D` 的话，子依赖（ICU、clang 工具链等）可能还是新版本的，遇到奇怪的编译错误先检查这一步。

### 网络受限环境

GitHub / googlesource 大包（>1GB）在 HTTP/2 下容易断流，配 HTTP/1.1 + 低速断线重试：

```bash
git -c http.version=HTTP/1.1 -c http.lowSpeedLimit=20000 -c http.lowSpeedTime=20 \
    fetch --depth 1 origin <sha>
```

失败时删掉 `.git/*tmp_pack*` 再重试。

## 构建

### Debug 构建

```bash
tools/dev/v8gen.py x64.debug
ninja -C out/x64.debug d8
```

### Release 构建

```bash
tools/dev/v8gen.py x64.release
ninja -C out/x64.release d8
```

Release 构建没有 DCHECK（`v8_enable_slow_dchecks` 类检查只存在于 debug），跑 PoC 更快；但调试时缺源码级断点信息，需要 gdb 符号的话加 `symbol_level=1`：

```bash
gn gen out/x64.release_sym --args='is_debug=false symbol_level=1 target_cpu="x64" v8_enable_object_print=true v8_enable_disassembler=true'
ninja -C out/x64.release_sym d8
```

调试构建的关键开关及含义（用 `gn args out/x64.debug --list` 查全量）：

| gn 参数 | 效果 |
|---|---|
| `is_debug=true` | 开启 DCHECK、慢检查、禁用优化 |
| `symbol_level=1/2` | 符号级别（2 = 全量 DWARF，编译慢） |
| `is_component_build=true` | 拆成 `libv8.so`，链接快但运行时加载慢 |
| `v8_enable_object_print=true` | `%DebugPrint` 输出完整对象结构 |
| `v8_enable_disassembler=true` | `--print-code` 等反汇编输出 |
| `v8_enable_verify_heap=true` | 每次分配时校验堆完整性（极慢，仅排查堆破坏） |

### 验证

```bash
./out/x64.debug/d8 --version
```

## d8 启动参数

### 基本模板

```bash
./out/x64.debug/d8 poc.js \
  --allow-natives-syntax \
  --print-bytecode \
  --print-bytecode-filter=trigger \
  >stdout.v8dump 2>stderr.v8dump
```

### 参数表

| 参数 | 说明 |
|---|---|
| `--allow-natives-syntax` | 启用 `%DebugPrint`、`%OptimizeFunctionOnNextCall` 等 `%` 内建 |
| `--print-bytecode` | 输出 Ignition 字节码 |
| `--print-bytecode-filter=<fn>` | 只输出指定函数的字节码 |
| `--print-opt-code` | 输出优化后的机器码 |
| `--trace-opt` | 输出优化编译触发日志 |
| `--trace-deopt` | 输出 deoptimization 日志 |
| `--trace-ic` | 输出 IC（inline cache）状态迁移 |
| `--trace-turbo` | 输出 TurboFan 优化过程 JSON |
| `--trace-turbo-filter=<fn>` | 只跟踪指定函数 |
| `--trace-turbo-path=<dir>` | TurboFan 图输出目录 |
| `--predictable --random-seed=1337` | 固定随机种子，提升复现确定性 |
| `--maglev` / `--no-maglev` | 手动开/关 Maglev 层 |
| `--no-turbofan` | 只跑 Maglev 及以下（分层隔离用） |
| `--jitless` | 全解释执行（排除 JIT 因素用） |
| `--expose-gc` | 允许 JS 调 `gc()`（**注意**：强制 GC 不增 SFI 年龄，不能替代自然 GC 冲刷） |
| `--sandbox-testing` | 沙箱实验 API（`Sandbox.getAddressOf` / `Sandbox.MemoryView`），配合 V8 沙箱研究用 |

参数名随版本可能变动，全部以 `d8 --help` 输出为准。

### `%` 内建函数

```javascript
%DebugPrint(obj);                          // 打印对象内部结构（地址/map/elements/length）
%SystemBreak();                            // 触发 SIGTRAP，gdb 接管
%PrepareFunctionForOptimization(f);        // 标记 f 为待优化
%OptimizeFunctionOnNextCall(f);            // 下次调用时强制 TurboFan
%OptimizeMaglevOnNextCall(f);              // 下次调用时强制 Maglev
%HasSmiElements(arr);                      // 检查数组元素种类
%NeverOptimizeFunction(f);                 // 永不优化（对照组）
```

## gdb

### 接入 V8 专用命令

V8 仓库自带 `tools/gdbinit`（提供 `job` / `jlh` 等命令）：

```bash
cp tools/gdbinit ~/.gdbinit_v8
echo 'source ~/.gdbinit_v8' >> ~/.gdbinit
```

### 启动

```bash
gdb --args ./out/x64.debug/d8 poc.js --allow-natives-syntax
```

```gdb
(gdb) set pagination off
(gdb) run
(gdb) bt
(gdb) x/20gx $rsp
```

### v8 gdb 命令

| 命令 | 说明 |
|---|---|
| `job <tagged_ptr>` | 打印 V8 对象（等价于增强版 %DebugPrint） |
| `jlh <local_handle>` | 通过 local handle 打印对象 |
| `jh <internal_handle>` | 通过 internal handle 打印对象 |
| `jco [pc]` | 打印 PC 对应的 Code 对象 |
| `jca [pc] [n]` | 打印附近反汇编 |
| `jst` / `jstc` | 打印 JS 调用栈 |
| `jtt <map>` | 打印 map 的 transition 树 |

### 常见断点

```gdb
(gdb) rbreak Builtins_                                  # 所有 builtin
(gdb) b v8::internal::Runtime_ThrowReferenceError       # 特定 runtime
(gdb) b v8::internal::BytecodeGenerator::VisitForStatement  # 字节码生成器
```

组件构建（`is_component_build=true`）时符号在 `libv8.so` 里，d8 本体很小——先 `set breakpoint pending on` 再下断点。

### 配合 JS 侧

1. JS 中 `%DebugPrint(obj)` 拿对象地址
2. JS 中 `%SystemBreak()` 在关键行断下
3. gdb 中 `job <addr>` 查看对象
4. `--print-bytecode --print-bytecode-filter=<fn>` 确认函数在断点处是否已编译

## 漏洞分析流程

```text
① 获取修复 CL / commit → 切到父提交 → 构建
② 最小化 PoC → 确认稳定触发（debug 崩 / release 行为异常）
③ 输出 bytecode → 确认前端语义和控制流正确
④ 对比 --jitless / --no-turbofan / 默认 的行为 → 判断哪层出问题
⑤ %DebugPrint 打印关键对象（receiver / 返回值 / 数组 backing store）
⑥ --trace-opt / --trace-deopt / --trace-ic / --trace-turbo 看优化过程
⑦ gdb 断点定位 → 对照 patch 确认根因路径
```

## 速查

```bash
# 源码
fetch v8 && gclient sync
git checkout <commit> && gclient sync -D

# 构建
tools/dev/v8gen.py x64.debug && ninja -C out/x64.debug d8

# bytecode
./out/x64.debug/d8 poc.js --print-bytecode --print-bytecode-filter=trigger

# opt / deopt / IC
./out/x64.debug/d8 poc.js --allow-natives-syntax --trace-opt --trace-deopt --trace-ic

# TurboFan 图
mkdir turbo && ./out/x64.debug/d8 poc.js --trace-turbo --trace-turbo-path=./turbo --trace-turbo-filter=trigger

# 分层隔离
./out/x64.debug/d8 poc.js --jitless          # 全解释
./out/x64.debug/d8 poc.js --no-turbofan      # 只到 Maglev

# gdb
cp tools/gdbinit ~/.gdbinit_v8 && echo 'source ~/.gdbinit_v8' >> ~/.gdbinit
gdb --args ./out/x64.debug/d8 poc.js --allow-natives-syntax
```
